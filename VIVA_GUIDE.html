1. Project Overview

Student portal consolidates events, registration, clubs, announcements, notifications, feedback. Four roles (STUDENT, ORGANIZER, FACULTY, ADMIN). JWT auth. Spring JDBC (not JPA). Swing desktop client calls REST API.

2. Architecture (draw this)

Swing Client → REST Controller (/api/events, /api/registration, /api/auth) → Service Layer (business rules) → DAO (parameterized SQL) → MySQL

3. Key Design Choices & Why

  • Spring Boot 3.5 + Gradle 8.14 + Java 21: modern LTS, compatible with course
  • JDBC Template instead of JPA: explicit SQL control, easier to explain row-locking and venue overlap queries in viva
  • JWT + Spring Security: stateless auth, role-based endpoint protection
  • SELECT ... FOR UPDATE: prevents race conditions on event approval/cancel/edit
  • No stored registered_count: derived live from registrations table (no drift)
  • Interface-based notification (EventCancellationNotifier): clean split with Member 6

    • 4. Member 3 (Event) — Files & Purpose

    Event.java — immutable record (id, venue, times, capacity, status, creator, reviewer)

    EventStatus.java — PENDING_APPROVAL / APPROVED / REJECTED / CANCELLED

    EventIntegrationTestSupport.java — MySQL fixtures for integration tests

    5. Contract Compliance (what your viva examiner asks)

  • Venue clash: LOWER(TRIM(venue)) + start_time < end_time AND end_time > start_time for APPROVED/PENDING events only
  • Approval: server-set PENDING_APPROVAL; approval requires venue re-check; rejection requires non-empty reason
  • Edit: only owner + only PENDING/REJECTED; edit clears review metadata and resets to PENDING_APPROVAL
  • Cancel: approved + pending only; coordinates notifications + registration cancellation in one @Transactional call
  • Student feed: role-scoped; students see only APPROVED events regardless of filter
  • Capacity: positive only; edit cannot lower below confirmed count
  • No SQL injection: all queries parameterized (PreparedStatement / JdbcTemplate)

    • 6. Testing Strategy

    Unit/integration against real MySQL (FOR UPDATE + unique constraints cannot be embedded). Fixtures in EventIntegrationTestSupport create users by role, insert events directly, clean tables between tests. Tests cover: create/edit/approve/reject/cancel/venue-conflict/capacity/permissions.

    8. Security

  • BCrypt password hashes
  • JWT access token returned on login
  • @PreAuthorize / Spring Security + service-level role checks (not just endpoint)
  • Every protected action verifies user.role + enabled + ownership

    • 10. Viva Q&A — Expected Questions

    Viva Q: Why JDBC over JPA? A: Explicit SQL control, easier to explain venue overlap and row-locking in viva.
    Viva Q: How do you prevent overbooking? A: SELECT ... FOR UPDATE + unique (student_id, event_id) + capacity check in same tx.
    Viva Q: What if two users approve at same time? A: Row lock (FOR UPDATE) serializes; only one approves; second waits on lock.
    Viva Q: How is venue conflict checked? A: Normalized venue equality + overlapping time ranges; re-checked at approval time.
    Viva Q: Why no registered_count column? A: Derived from registrations table — avoids drift.
    Viva Q: How does cancellation work transactionally? A: @Transactional in EventService.cancel() updates event + writes notifications + calls registration cancellation — all on same connection.
